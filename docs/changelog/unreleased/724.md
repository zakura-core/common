## zakura-transparent

### Added

- Added opt-in SLH-DSA-SHA2-128f and SLH-DSA-SHA2-192s key generation, signing,
  and verification through the `pq` feature, behind a dedicated transparent output
  type. An output of the one format defined here is 35 bytes: `OP_0` naming the
  format, the small-integer opcode naming the signature scheme within it, and a
  32-byte push of `SHA-256` over the committed script. The output carries both
  bytes, so validation can classify an output when it is created rather than when
  it is spent, and reject an undefined one while the sender still holds the coins.
  The namespace claims every format opcode, every scheme opcode, and every
  commitment length a single direct push can carry, so everything in it that this
  format does not define is restricted rather than spendable: it cannot be
  created, cannot be spent, and cannot be expressed through the builder, which
  takes a parameter set rather than a script. The scheme selects the signature
  parameter set and the signing context, and the format fixes the commitment, so a
  later format can change what the commitment is while the schemes keep their
  numbers inside it. Both bytes appear only in the output. Spends authenticate that commitment, require a canonical serialized
  input, and share existing script operations and multisig rules. These APIs cover
  PQ outputs only, so every other output keeps the evaluator and flags it uses
  today, and legacy outputs stay creatable and spendable. Callers supply a trusted
  previous output and transaction checker; these APIs do not activate PQ outputs
  ([#724](https://github.com/zakura-core/common/pull/724)).
- Added `TransparentBuilder::add_pq_output`, which pays a PQ commitment under a
  chosen parameter set ([#724](https://github.com/zakura-core/common/pull/724)).
- Added `util::sha256::hash`, a one-shot SHA-256
  ([#724](https://github.com/zakura-core/common/pull/724)).
- Added `pq::template`, which builds the one committed script a wallet must use for
  an address it issues from a derived key — a single public key and a signature
  check — along with that script's commitment and the output paying it. An output
  commits to a script and carries nothing but its hash, so without a fixed shape an
  address would need the script backed up separately; with it, an address is a
  function of the derived key alone. Any other script stays legal and
  indistinguishable on chain, and the wallet that commits to one owns its backup
  ([#724](https://github.com/zakura-core/common/pull/724)).
- Added `pq::ParameterSet::address_scheme` and `from_address_scheme`, which convert
  between a parameter set and the scheme a Unified Address receiver names
  ([#724](https://github.com/zakura-core/common/pull/724)).

### Changed

- The second header byte of a post-quantum output is now called its scheme rather
  than its version: `pq::ParameterSet::scheme`, `scheme_opcode`,
  `scheme_from_opcode`, `from_scheme`, and `pq::output::Error::UnsupportedScheme`.
  Byte 0 is the format and byte 1 the scheme within it, and one name for both
  invited the reading that there is a single version layer. No encoding or behavior
  changes ([#724](https://github.com/zakura-core/common/pull/724)).

## zakura-address

### Added

- Added a post-quantum transparent receiver to the Unified Address encoding:
  `unified::PqScheme`, the `unified::Typecode::PqTransparent` and
  `unified::Receiver::PqTransparent` variants, and the provisional typecodes
  `unified::PQ_SHA2_128F_TYPECODE` and `unified::PQ_SHA2_192S_TYPECODE`. A receiver
  carries the bare 32-byte commitment its output holds, and a sender rebuilds the
  output from it. It counts as a transparent receiver, so it may not be the only
  receiver in an address that owes a shielded one; it may accompany one legacy
  transparent receiver, which is what makes adoption additive; it ranks above both
  legacy transparent receivers and below both shielded pools; and at most one may
  appear per address. It cannot appear in a viewing key, because a hash-based
  public key cannot be derived without the secret that generates it. The typecodes
  are provisional until the ZIP process assigns them
  ([#724](https://github.com/zakura-core/common/pull/724)).

## zakura-keys

### Added

- Added `UnifiedAddress::with_pq_transparent_receiver`, `has_pq_transparent` and
  `pq_transparent`, and a Unified Address whose only transparent receiver is the
  post-quantum one now reports that it can receive a transparent payment. The
  receiver is supplied by the caller rather than derived, because a hash-based
  public key has no derivation from a viewing key: the commitment comes from the
  key pool that generated it
  ([#724](https://github.com/zakura-core/common/pull/724)).

## zakura-zcash-script

### Added

- Added a raw-signature checking hook that preserves ECDSA behavior by default,
  and an opt-in `pq` evaluator with bounds for larger serialized arguments and
  stack payloads. The PQ evaluator additionally requires minimally encoded input
  pushes, an empty multisig dummy argument, and a single final stack item, none of
  which the legacy evaluator enforces by default
  ([#724](https://github.com/zakura-core/common/pull/724)).
- Added `script::is_pq_namespace`, `script::PQ_NAMESPACE_HEADER_BYTES`,
  `script::PQ_NAMESPACE_MIN_BYTES` and `script::PQ_NAMESPACE_MAX_BYTES`, which
  recognize the post-quantum output namespace, and
  `interpreter::Flags::PqOutputs`, which makes the legacy evaluator return the new
  `script::Error::PqNamespace` rather than evaluating such a script — as a
  `scriptPubKey` or as a P2SH redeem script. Without that flag the legacy rules
  satisfy one of these scripts with an empty scriptSig, so a verifier that
  activates the post-quantum rules must set it. Note that it occupies the bit
  Bitcoin Core uses for `SCRIPT_VERIFY_CHECKSEQUENCEVERIFY`, which Zcash does not
  implement, so a boundary forwarding raw script-verification flags should mask
  the bits it does not mean ([#724](https://github.com/zakura-core/common/pull/724)).
